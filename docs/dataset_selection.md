Your detector counts events per minute, so a dataset must pass three tests. The first test is **real arrival times and source IPs in raw log format**. Without them, request rate, distinct URLs and events-per-user would only reflect the replay schedule you invented. The second is **a clean normal-only period**, because all three models train on normal windows only. The third is **labels you can map to 1-minute windows**. AIT-LDS v2.0 passes all three tests for both lanes. Each of its 8 testbeds is a small simulated company with a mail server, file share, WordPress server, VPN and firewall. The collected logs include Apache access and error logs and authentication logs. Each scenario runs **4–6 days**, and the attack happens in a single window of **45 minutes to 10 hours** ([Zenodo AIT-LDS v2.0](https://zenodo.org/records/5789064)). Labels sit in a `labels/` folder that mirrors the log folder. Every attack-related line has a JSON entry with its line number and attack-step names, and **every line without an entry counts as normal** ([Zenodo AIT-LDS v2.0](https://zenodo.org/records/5789064)). The peer-reviewed paper (IEEE TDSC, 2023) describes the normal users as state machines that drive real browsers for three user types, with working hours of roughly 05:00–22:00. The authors also checked realism: simulated users produced **307.2 DNS events per day** against **306.2** for real people in a cyber exercise ([Landauer et al.](https://ar5iv.labs.arxiv.org/html/2203.08580)).

The Wazuh connection is what makes this dataset easy to defend. AIT replayed the same logs through Wazuh, Suricata and their own AMiner detector, and published **2,655,821 alerts (86% from Wazuh)** together with a `labels.csv` that gives the start and end time of each attack phase, under CC BY 4.0 ([Zenodo AIT-ADS](https://zenodo.org/records/8263181)). One example alert is Wazuh rule **5304 "User successfully changed UID"** from `/var/log/auth.log` at 04:37:40 in russellmitchell, which falls inside that scenario's attack window ([CSET 2024 slides](https://cset24.isi.edu/slides/cset2024-slides-landauer.pdf)). The plan follows from this. Replay the AIT logs through *your own* Wazuh, so the rule baseline matches your deployment, and use AIT-ADS only as a sanity check: if your replay also raises rule 5304 on the `su` step, your pipeline works. AIT's own AMiner baseline trained on the **first two days** of each scenario, which gives you a precedent for your training split ([CSET 2024 slides](https://cset24.isi.edu/slides/cset2024-slides-landauer.pdf)).

## AIT-LDS covers the web lane well but leaves the SSH lane almost empty

The AIT attack chain is nmap scans, WPScan and dirb scans, a webshell upload through the wpDiscuz plugin (CVE-2020-24186) followed by commands, a database dump, password cracking with John the Ripper, login as a system user (privilege escalation), a reverse shell, and DNS exfiltration ([Zenodo AIT-LDS v2.0](https://zenodo.org/records/5789064); [Landauer et al.](https://ar5iv.labs.arxiv.org/html/2203.08580)). **The web lane fits well.** The dirb scan sends several thousand requests in a short time. In santos, intranet-server accesses jumped from several hundred to **more than 5,000** during the scan, and webshell commands appear directly in URLs ([Landauer et al.](https://ar5iv.labs.arxiv.org/html/2203.08580)). Your request-rate, distinct-URL and 404 features should react strongly. **The SSH lane does not fit well.** On auth.log, AIT only shows the escalation step (`su`, UID change) and normal admin SSH sessions. There is no brute force and no password spraying. The password cracking runs offline, so it leaves no failed logins in auth.log. Only users with an SSH admin role log in, using a fixed command list ([Landauer et al.](https://ar5iv.labs.arxiv.org/html/2203.08580)), so most auth minutes will show only 0–2 events. The older AIT-LDS v1.1 includes a hydra brute-force step, but its target is most likely the Horde webmail login rather than sshd (this is unverified). Its labels are also "not guaranteed" correct ([Zenodo AIT-LDS v1.1](https://zenodo.org/records/4264796)). Do not build your SSH lane on it.

The lab is therefore needed for **coverage**, not just convenience, and this is the strongest argument for it. Recent work closest to your project did the same thing. A 2026 Wazuh-focused paper states that no public labelled dataset exists for multi-class web attacks in Wazuh event format. Its authors built their own: OWASP Juice Shop with a Wazuh agent on the Apache log, Selenium for normal traffic, and sqlmap, Gobuster, Burp Suite and other tools attacking from separate IPs. Labels came from attacker IP plus recorded timestamps, giving 46,454 Wazuh events ([Alboushy et al., arXiv 2605.13337](https://arxiv.org/abs/2605.13337)). Your lab follows the same pattern. The table below shows where each target attack comes from. The last column is a **hypothesis** that your per-attack results will confirm or reject.

| Attack type | Lane | Source | Feature expected to react (hypothesis) |
|---|---|---|---|
| Fast SSH brute force (hydra) | SSH | Lab | event_count, events_per_user, max_rule_level |
| Password spraying (one password, many users) | SSH | Lab | distinct_users |
| Low-and-slow guessing (1 try every few minutes) | SSH | Lab | Almost none at 1-minute granularity, so a miss is expected |
| Distributed brute force (many source IPs) | SSH | Lab | Distinct source IPs, event_count |
| Unusual-hour login | SSH | Lab (+ AIT russellmitchell at night) | hour |
| Success after many failures | SSH | Lab | max_rule_level, only if a Wazuh rule fires |
| Privilege escalation (`su`, UID change) | SSH | AIT | max_rule_level |
| Content discovery (dirb, gobuster, WPScan, nikto) | Web | AIT + Lab | Request rate, distinct URLs, 404 count |
| Webshell commands in URL | Web | AIT | Distinct URLs (weak) |
| SQLi, XSS, path traversal | Web | Lab | Weak for count features; Wazuh signatures likely stronger |
| HTTP login brute force | Web | Lab | Request rate on one URL, error ratio |
| Crawler flood | Web | Lab | Request rate, distinct URLs |

Build the lab in the same shape as AIT, so that one protocol works for both. Start a benign traffic generator **at least three days before the first attack** and keep it running during the attack days. That gives you two training days and one validation day, exactly as on AIT. For SSH, use cron jobs that log in as three to five users and sometimes type a wrong password. Real users fail occasionally, and without that noise any single failure looks anomalous. For the web lane, use a crawler or Selenium/locust script that browses with a working-hours rhythm. Write every attack run into an `attack_schedule.csv` with start, end, attacker IP, attack type, tool and parameters. Give each attack type its own attacker IP, and use several IPs (containers or IP aliases) for the distributed attack. Run each attack type **two or three times** at different hours and intensities. AIT varies attack parameters across its scenarios for the same reason: detection should not depend on one setting ([CSET 2024 slides](https://cset24.isi.edu/slides/cset2024-slides-landauer.pdf)). Add one minute of padding after each scheduled end time for log-writing delay, which AIT names as a known labelling problem ([CSET 2024 slides](https://cset24.isi.edu/slides/cset2024-slides-landauer.pdf)), and state this in the report.

**CIC-IDS2017/2018 is the examiner's most likely suggestion, because it is the most-cited dataset for SSH brute force.** It has the wrong modality for your detector. CIC-IDS2017 releases packet captures and flow CSVs and lists no Linux auth logs or web-server logs ([UNB CIC-IDS2017](https://www.unb.ca/cic/datasets/ids-2017.html)). CSE-CIC-IDS2018 adds host logs, but a 2024 survey reports that the host data is **not labelled** and that the Ubuntu excerpt shows CRON and dhclient lines ([COMIDDS](https://arxiv.org/html/2408.02521v1)). The data also has known quality problems. Engelen et al. found that **more than 25% of CICIDS2017 flows are meaningless artefacts**, reaching about 50% for some attack classes, and that the problem continues in the 2018 set ([Engelen et al. 2021](https://lirias.kuleuven.be/retrieve/713070)). When HTTP2vec rebuilt web requests from the 2018 packet captures, every attack URI started with `/DVWA` and every attack carried an extra header, and all classifiers scored **F1 0.999**. The authors themselves suspected the dataset was too simple ([HTTP2vec](https://arxiv.org/pdf/2108.01763)). The often-quoted 99% results for SSH brute force come from **supervised** flow classifiers, for example AUC and AUPRC above 0.99 with a decision tree on two features ([Hancock et al.](https://archive.cps-vo.org/node/85619)). Those numbers cannot be compared with an unsupervised host-log detector.

**LANL 2015 is the classic unsupervised authentication benchmark, but it is Windows.** Its `auth.txt` holds Windows and Active Directory logon events with users, computers, auth type and success flag. It has no sshd lines, no IP addresses and no syslog text, so Wazuh cannot produce `max_rule_level` from it ([LANL](https://csr.lanl.gov/data/cyber1/)). Red-team events are under **0.001%** of the data, and the attacks are credential misuse and lateral movement, not brute force ([Tuor et al.](https://arxiv.org/pdf/1712.00557)). It is still useful as a reference point. On LANL, Isolation Forest scored **AUC 0.763** at user-day level, against 0.97–0.98 for recurrent language models at log-line level ([Tuor et al.](https://arxiv.org/pdf/1712.00557)). The gap shows how strongly aggregation level shapes the score.

**CSIC 2010 is the standard web-attack benchmark, but it is a bag of requests.** It has **no date or time fields**, and every record has the same Host value ([CSIC mirror](https://github.com/msudol/Web-Application-Attack-Datasets)), so per-minute request rate or 404 counts would be inventions. Its published results are also at request level: supervised F1 around 0.95–0.97, and **F1 0.84** for an autoencoder plus Isolation Forest ([HTTP2vec](https://arxiv.org/pdf/2108.01763)). The other options fail for similar reasons. LogHub OpenSSH and SecRepo are real, but they have no labels ([LogHub](https://github.com/logpai/loghub)). If you labelled them with rules, the AI-vs-Wazuh comparison would become circular, because the rules would define the truth. Honeypots contain no benign traffic, so normal-only training is impossible. SR-BH 2020 came from an internet-facing server where **42% of requests are anomalous**, so it has no clean normal period ([SR-BH 2020](https://dataverse.harvard.edu/api/datasets/:persistentId/?persistentId=doi:10.7910/DVN/OGOIXX)). The raw Zaker 2019 nginx log is now **restricted** on Dataverse ([Zaker 2019](https://dataverse.harvard.edu/api/datasets/:persistentId/?persistentId=doi:10.7910/DVN/3QBYB5)).

So why not use several public datasets? Because, for this log type, **no second public dataset passes the three tests**. In practice, "several datasets" means several AIT scenarios plus your lab, which gives you two independent environments. That design also matches published advice. Arp et al. recommend checking results from well-known datasets against newer data from the real application domain ([Arp et al., USENIX Security 2022](https://arxiv.org/abs/2010.09470)). Le and Zhang found that log anomaly detectors often fail to generalise across experimental settings ([Le & Zhang, ICSE 2022](https://arxiv.org/abs/2202.04301)). Train and threshold each environment on its own normal period. Keep the window size, features, threshold rule and metrics identical across environments. Do not claim that a model transfers from AIT to the lab unless you test that directly.

## Train on early normal days, freeze the threshold, report per attack

**Split by time, never at random.** For each scenario and each lane, train on days 1–2, use day 3 as a normal-only validation day, and test on the attack day and any days after it. For example, russellmitchell trains on 21–22 January, validates on 23 January and tests on 24–25 January. Le and Zhang showed what a random split does: DeepLog on BGL scored **F1 0.927 with a random split but 0.426 with a time-ordered split** ([Le & Zhang](https://arxiv.org/abs/2202.04301)). Fit scalers on training windows only. Arp et al. warn that computing statistics over the whole dataset leaks test information ([Arp et al.](https://arxiv.org/abs/2010.09470)). AIT deliberately runs its DNS exfiltration from the start of each simulation ([Landauer et al.](https://ar5iv.labs.arxiv.org/html/2203.08580)). That only touches DNS logs, which you do not use, so your auth and web training days stay clean. Say this before an examiner asks.

**Label windows from lines, and bucket by the original log time.** A window counts as positive if it contains **at least one labelled line** in that lane, which is the standard convention ([Le & Zhang](https://arxiv.org/abs/2202.04301)). Keep the attack-step names for each window so you can compute recall per attack. Two practical traps apply when you replay 2022 logs in 2026. First, bucket each window on the timestamp inside the log line, not on the time Wazuh received it. Syslog lines have no year, so take the year from `dataset.yml`. Second, make sure your feature builder sees **every** log line, not only the lines that became Wazuh alerts. Wazuh writes alerts only for rules above its alert level, so ordinary access-log lines can be missing from the alert output. If they are missing, enable Wazuh's archive output or count from the raw files. Otherwise request rate and event_count will be wrong.

**Fix one threshold rule from normal data, and freeze it before testing.** Set the threshold from validation-day scores only. One option is the 99.5th percentile, which allows about 7 alerts per normal day of 1,440 windows. Another is a fixed alert budget. No source prescribes one percentile, so state your choice and keep it. Apply the **same rule** to the Isolation Forest score, the autoencoder reconstruction error and the DFP loss, so the three models compete fairly. Arp et al. list test-set tuning of parameters as a common pitfall ([Arp et al.](https://arxiv.org/abs/2010.09470)). Morpheus DFP was built for per-user fingerprints. If you feed it the same window features as the other two models, say so. If you feed it different inputs, report that difference. No published evaluation of DFP on AIT-LDS or on count windows was found, so your numbers will be new, and you should present them as new rather than as comparable to earlier work.

**Report PR-AUC and false alarms per day, not accuracy.** In fox, the attack lasts **76 minutes** inside a simulation of about **7,200 one-minute windows**, roughly 1% (computed from the Zenodo times). A detector that never raises an alert would score **about 99% accuracy**. Arp et al. show that on a 1:100 class ratio, a detector with 99% true-positive rate at 1% false-positive rate produces about **100 false alarms for every 99 real detections** ([Arp et al.](https://arxiv.org/abs/2010.09470)). At 1,440 windows per day, a 1% false-positive rate means about **14 false alarms per day per lane**, a number an examiner understands immediately. Your primary metric should be PR-AUC (average precision). Next to it, report precision, recall and F1 at the frozen threshold, plus false-positive rate and false alarms per day. Use ROC-AUC only as a secondary metric. Run Isolation Forest and the autoencoder with five random seeds and report mean ± standard deviation across seeds and scenarios. Do not use point adjustment, where a whole attack segment counts as detected if any single window in it is flagged. Kim et al. show that under point adjustment, **even random scores can look state-of-the-art** ([Kim et al.](https://arxiv.org/abs/2109.05257)). Report "attack detected: yes/no" in its own column instead.

**Compare against two baselines and run two ablations.** The first baseline is **Wazuh rules** on the same logs. Mark a window as flagged when it contains at least one alert at level X or above, state X, and show two or three values of X. The second is a **trivial count threshold**, such as an IQR (box-plot) rule on event_count. Do not skip it. In Arp et al.'s case study, a box-plot threshold on packets per window beat a published autoencoder ensemble (**AUC 0.998 vs 0.968**), because the lab attack was too obvious ([Arp et al.](https://arxiv.org/abs/2010.09470)). If your autoencoder does not beat the count rule on AIT's loud dirb scan, report that honestly. Then run two cheap ablations. **Without the `hour` feature:** the russellmitchell attack runs at 03:01–04:39 while simulated work runs about 05:00–22:00 ([Landauer et al.](https://ar5iv.labs.arxiv.org/html/2203.08580)), so the hour alone might flag it. **Without `max_rule_level`:** this feature comes from Wazuh, so the AI may simply be copying the rules. Showing results without it proves the AI adds its own signal. Finally, report **time to detect** for each attack step: the time from the first labelled line (or scheduled start) to the first flagged window, for each model and for Wazuh. Le and Zhang treat early detection as a separate evaluation dimension ([Le & Zhang](https://arxiv.org/abs/2202.04301)).

Set your expectations from the closest published work. In the 2026 Wazuh paper, native Wazuh rules detected **0% of brute-force and broken-authentication web events**, while the ML module detected 100% and 98.3% ([Alboushy et al.](https://arxiv.org/abs/2605.13337)). ## How to answer the examiner in under a minute

Memorise this core answer: *"My detector works on one-minute windows of Wazuh-decoded auth.log and Apache logs, and it trains on normal data only. A dataset must therefore have raw logs with real timestamps and IPs, a clean normal period and line-level labels. AIT-LDS v2.0 is the only public dataset I found that meets all three for both lanes. It is peer-reviewed in IEEE TDSC, its labelling method is published, and AIT has already replayed it through Wazuh. It has no SSH brute force, so I added scripted lab attacks with exact timestamps. I evaluate both environments with the same time-ordered protocol."*

| Why not real logs? | The public real logs (LogHub, SecRepo) have no labels. Labelling them with rules would make the AI-vs-Wazuh comparison circular. |
| Why only one public dataset? | No second public dataset passes the three tests. I use several AIT scenarios with different timing and scan intensity, plus an independent lab, as Arp et al. recommend ([Arp et al.](https://arxiv.org/abs/2010.09470)). |
| Can we trust lab or synthetic data? | Partly, and I say so. Scripted normal traffic makes the false-positive rate optimistic. This is the "lab-only evaluation" pitfall, found in 47% of papers Arp et al. reviewed ([Arp et al.](https://arxiv.org/abs/2010.09470)). My trivial count baseline shows when an attack is simply too loud. |
| Why not accuracy? | Attack windows are about 1% of all windows, so a detector that never alerts gets about 99% accuracy. I report PR-AUC and false alarms per day instead. |
| Did you tune on the test set? / Is it just the hour or just Wazuh? | No. The threshold is frozen from the normal validation day, with the same rule for all models. Ablations without `hour` and without `max_rule_level`, plus the daytime fox scenario, answer the other two questions. |

## Conclusion

The missing dataset is itself a finding you can use. No public, labelled dataset exists with SSH and web logs in Wazuh-compatible format and the attack types you need. The 2026 Wazuh paper reached the same conclusion for web attacks ([Alboushy et al.](https://arxiv.org/abs/2605.13337)). If you publish your lab capture with its attack schedule and scripts, the project gains a small but real contribution, plus a reproducibility advantage. Only **8 of 62** log anomaly-detection papers in one survey released their code ([Landauer et al. survey](https://arxiv.org/html/2207.03820v2)).

Expect a map of complementary strengths, not a simple "AI beats Wazuh" result. One-minute count features should catch loud scans, floods and fast brute force, where rules are weak. Signature rules should catch single SQLi or traversal payloads, which barely change a minute's counts. Low-and-slow guessing will probably beat both at one-minute granularity, and you should present that as a limitation that motivates longer windows in future work, not as a failure. Examiners trust an honest coverage map, backed by a frozen threshold and a trivial baseline, more than a single high F1 score.
